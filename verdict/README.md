# Verdict MVP

Verdict 帮 PayPal 商家处理争议和退款：收集买家证据，判断真实性和充分性，给出带理由的报告。资金动作必须由商家确认后才执行。

这是可以直接试用的最小版本，不需要外部服务或密钥。控制台需要登录，第一次启动时创建店主账号（见下文）。默认情况下 PayPal 和物流都由内置模拟器代替，**不产生真实资金流动**。也可以[接 PayPal 沙箱](#接-paypal-沙箱可选)，用测试资金走真实接口。

## 运行

需要 Node.js 22.13 或更高版本。

```bash
npm install
```

```bash
npm run dev
```

打开 <http://127.0.0.1:3000>。首次访问会自动生成演示数据，存放在 `.data/`。

**第一次登录：** 还没有账号时，服务端终端会打印一条创建店主账号的链接：

```
[verdict] http://127.0.0.1:3000/setup?token=...
```

打开它，填名字、邮箱和密码（至少 10 位）即可登录。找不到这条输出时运行：

```bash
npm run account-link
```

链接只打印在终端和 `.data/setup-token` 里，不会出现在网页上：同一网络里的其他人，或者伪装成本机的网页，拿不到它，也就没法抢先注册店主。

其他命令：

| 命令 | 作用 |
|---|---|
| `npm test` | 运行判定引擎、18 个验收场景、服务端、核验报告 PDF、PayPal 沙箱客户端、设置、数据删除、订单推送、账号与安全、影子模式、视频证据、评估集的测试。沙箱测试用模拟响应，不访问网络；视频测试需要 ffmpeg，没有时跳过 |
| `npm run typecheck` | 类型检查 |
| `npm run eval` | 跑评估集，输出精确率、召回率、误判率、稳健性等指标，见下文“评估集” |
| `npm run reset` | 删除 `.data/`，下次启动时重新生成（需先停止服务）。账号也会一起删掉，需要重新创建店主。只想恢复演示数据时用“设置”页的重置，账号和 PayPal 凭证会保留 |
| `npm run account-link` | 还没有账号时打印创建店主的链接；`npm run account-link -- 邮箱` 给这个账号生成重置密码链接（店主忘记密码时用） |
| `npm run dev:phone` | 用手机测试摄像头，见下文 |

## 三种试法

**1. 看验收场景。** 索赔列表里的 18 笔对应开发文档的验收表。每笔都标了场景和文档期望，可以和实际判定对照。

**2. 走一遍买家流程。** 进入“订单与留底”，打开一笔订单，点“生成索赔链接”，再打开买家页面：确认订单、选问题类型、逐镜头拍摄（每个镜头有随机挑战码）、提交。回到商家端可以看到分析器逐项完成、判定随之更新。电脑没有摄像头时，可以从相册选择，这类证据按 C 层降权。

**3. 试你自己的图片。** 点“手动导入”，上传一张 ChatGPT 生成的图或任意照片。没有配置 LLM 时，只有本地分析器会运行，判定会标“核验不完整”并列出没跑的检查。

在订单页点“模拟 PayPal 争议”，可以走完 webhook 验签、去重、拉取详情、建索赔的流程。

## 哪些是真的，哪些是模拟的

| 部分 | 状态 | 说明 |
|---|---|---|
| 判定引擎、硬规则、R/Q/M 计算 | 真实运行 | 确定性规则，同样的输入得到同样的结果 |
| Provenance | 真实运行 | 按字节扫描 C2PA 和 AIGC 隐式标识。只判断是否存在，**不校验签名** |
| Origin | 真实运行 | 256 位感知哈希，比对本商家历史证据。反向搜图未接入 |
| Logistics、Behavior | 真实运行 | 逻辑是真的，物流数据来自模拟器（沙箱订单也一样） |
| 动作执行、幂等、确认校验、token | 真实运行 | 只有 `src/server/actions.ts` 能调用 PayPal 写接口，由测试保证 |
| PayPal | **模拟**，可接沙箱 | 18 个演示场景始终走模拟器。配置沙箱后，沙箱订单调用真实的 PayPal 沙箱接口。不支持正式环境 |
| 演示场景的视觉分析和检测器结果 | **录制回放** | 18 个场景的结果预先写入缓存，走和真实调用相同的代码路径，界面标“录制回放” |
| 你上传的真实图片的视觉分析 | 默认不运行 | 需要配置 LLM，见下文 |
| AI 生成检测器、SynthID | 未接入 | 真实图片的 Synthetic 显示“未执行” |

演示图片都是程序画的占位图，右下角标有“演示占位图”。

## 核验报告 PDF

报告页右上角可以“下载 PDF”。提交反驳证据（`provide-evidence`）和申诉（`appeal`）时默认附上报告，文件名 `verdict-report.pdf`，排在证据图片前面。

报告有两个版本：

| 版本 | 用途 | 和网页报告的区别 |
|---|---|---|
| 商家版 | 下载存档 | 内容相同 |
| 提交版 | 随证据发给 PayPal，可在报告页“预览提交版” | 不含商家侧风险 M、内部提示、草稿、规则轨迹和 Behavior 分析器的发现（开发文档：内部风险标记不对外展示）。图片只用这笔索赔自己的证据和本订单的留底，复用检测引用的其他买家图片不会出现 |

PDF 要内嵌中文字体，字体不随仓库分发。系统会按顺序找 Noto Sans CJK、文泉驿、macOS 的华文黑体/宋体/Arial Unicode、Windows 的微软雅黑/黑体。都没有时：

- 报告页的“下载 PDF”返回 503 并说明原因；
- 提交证据照常进行，只附图片，动作记录里写明“没有附上报告”，动作面板的勾选框也会变灰。

也可以用 `VERDICT_REPORT_FONT` 指定字体文件，TTC 字体集要再用 `VERDICT_REPORT_FONT_FAMILY` 指定 PostScript 名称。

发现里引用的图片如果有可疑区域（例如复用检测找到的匹配位置），缩略图上会画红框，和网页一致。

## 视频证据

买家在索赔页可以切到“录视频”现场录一段（最长 15 秒），也可以从相册选视频；商家手动导入时，商品照片一栏也收视频。支持 MP4、MOV、WebM，单个视频不超过 40MB，一次请求不超过 48MB。

按开发文档“视频先用 ffmpeg 抽帧，帧作为图片输入其余分析器，原视频只给 Consistency 和 Provenance 使用”：

- **抽帧：** 固定间隔（2 秒或时长的十分之一，取大者）加场景切换，每段最多 12 帧。帧挂在视频下面，继承来源、证据层级、镜头和挑战码，上传时间和视频相同。
- **原视频：** Provenance 扫描容器里的 C2PA 清单（MP4/MOV 的 uuid 盒子）和元数据。元数据里有剪辑软件（剪映/CapCut、Premiere、Final Cut 等）时给出“视频经过剪辑软件处理”（强度中）；现场录制的视频出现硬切时给出“现场录制的视频中有画面突变”（强度弱）。这两项不依赖 LLM。
- **Consistency：** 看全部帧和原视频信息。挑战码只要在任意一帧里出现就算通过；数量取各帧中最多的一帧。
- **其他分析器**（Synthetic、Origin、Plausibility、Reference）只看帧。
- **提交给 PayPal：** 附件和 PDF 报告里用视频的第一帧代替视频本身。

抽帧要用服务器上的 ffmpeg 和 ffprobe（macOS：`brew install ffmpeg`）。找不到时会依次试 `FFMPEG_PATH`/`FFPROBE_PATH`、PATH、Homebrew 目录。没有 ffmpeg 时视频照样保存、照样能播放，但不抽帧：Consistency 和只看帧的分析器标为未执行，判定显示“核验不完整”。

请求体限制：Next.js 的 proxy 默认只缓冲 10MB 请求体，超出部分会被截掉，视频上传会变成一个坏文件。`next.config.ts` 里把 `experimental.proxyClientMaxBodySize` 调到了 48MB，和上传上限一致。

## 账号与权限

控制台按开发文档分两种角色：

| 能做什么 | 店主 | 客服 |
|---|---|---|
| 查看索赔、订单、报告，上传留底照，手动导入，生成索赔链接，重新分析 | ✓ | ✓ |
| 发消息、提交证据、补充说明、升级争议、申诉 | ✓ | ✓ |
| 退款、接受索赔、提出和解、确认收到退货（资金动作），以及核对这类动作的结果 | ✓ | |
| 管理成员、PayPal 凭证、判定设置，删除索赔数据，重置演示数据，沙箱测试下单和推进争议 | ✓ | |

界面上客服看到的资金动作按钮是灰的；服务端的动作执行器同样会拒绝，不依赖界面。

**添加成员：** 店主在“设置 → 成员”里填名字、邮箱和角色，系统生成一条设置密码的链接（72 小时内有效，只能用一次）。系统不发邮件，链接由店主自己发给对方。成员忘记密码时，店主点“重置密码”生成新链接；停用成员后，对方所有设备上的登录立即失效。至少要保留一个可用的店主。

**登录保护：**

- 密码用 scrypt（N=2^17）哈希后存储。
- 同一账号连续 5 次输错密码锁定 15 分钟，同一 IP 每分钟最多 20 次登录类请求。
- 会话 cookie 是 HttpOnly、SameSite=Lax，HTTPS 下加 Secure。连续 12 小时不操作或满 7 天失效。
- 修改或重置密码后，其他设备上的登录失效。
- 所有写接口拒绝跨站请求。页面禁止被其他网站嵌入 iframe。

**PayPal 凭证加密：** 店主可以在“设置 → PayPal 凭证”里填沙箱应用的 Client ID 和 Secret。保存前先向 PayPal 换一次令牌验证。Secret 用 AES-256-GCM 加密后存库，密钥来自环境变量 `APP_ENCRYPTION_KEY`（`openssl rand -hex 32` 生成），不进数据目录，所以数据库文件单独泄漏时读不出 secret。设置页保存的凭证优先于 `.env.local`；没有保存时仍然用 `.env.local`，原来的配置不受影响。没有配置 `APP_ENCRYPTION_KEY` 时不能在设置页保存。

**索赔页限流：** 买家索赔页的接口同时按链接和 IP 限流，比如提交每个链接每分钟 5 次、每个 IP 每分钟 10 次，超出返回 429。限流计数在进程内存里，只适合单进程部署。直连时客户端可以伪造 `X-Forwarded-For`，所以按链接限流才是主要防线；部署在反向代理后面时设 `TRUST_PROXY_HOPS`，就能拿到真实的客户端 IP。

## 设置

“设置”页可以改这些配置，对应开发文档的 `GET/PUT /api/settings`：

| 配置 | 说明 |
|---|---|
| 判定权重与阈值 | 强度权重、证据层级权重（按文档的四档：A/B、C 争议附件、C 相册上传、D）、中/高风险阈值、“Q 充足”和“M 高”的阈值。保存时校验：强 ≥ 中 ≥ 弱，A/B ≥ C ≥ D，高风险阈值大于中风险阈值。硬规则信号不受权重影响。“适用范围”可以选某个类目，给它单独一套（比如生鲜放低 Q 阈值）；没有单独配置的类目用商家默认，改商家默认不影响有专用配置的类目 |
| 影子模式 | 见下文“影子模式” |
| 类目策略 | 每个类目的可退货、易腐、涉及安全、核对序列号四个开关。订单里出现的新类目也会列出来。必需镜头的配置保留原样，页面上不能改 |
| 退货地址 | “退货退款”和解时发给 PayPal 的地址。不填时用演示地址（虚构） |
| 证据保留期 | 见下文“数据最小化” |

改了权重或类目策略后，受影响的未结案索赔会立即按新配置重新判定（只改某个类目的专用配置时只重算这个类目），判定等级变化的会写进时间线，保存结果里也会列出来。已结案的索赔保留当时的判定。每次判定都在审计记录里写明当时用的权重配置，用了类目专用配置的会写“类目“生鲜”专用配置”（网页报告、商家版 PDF）。

## 影子模式

开发文档的测试部分要求影子模式：判定只记录、不展示，用来和商家自己的实际决定对比。适合正式启用判定前先跑一段时间。店主在设置页开关。

开启后：

- 索赔列表不显示判定、R/Q/M，也没有按等级筛选；演示场景的标题和说明会透露判定，也隐藏
- 索赔详情不显示判定、分数、发现、命题核验和审计记录，不能打开核验报告（网页和 PDF 接口都拒绝）
- 动作面板只按 PayPal 当前允许的操作列出中性选项，没有“建议：”，草稿不引用任何核验发现
- 不附核验报告，也不自动附证据图片（自动挑选的图片来自反驳索赔的信号，数量本身就会透露判定），服务端同样强制
- `GET /api/claims` 和 `GET /api/claims/{id}` 返回的数据同样去掉了判定内容，不是只在界面上隐藏

动作仍然绑定当时的判定 ID，并记下是在影子模式下执行的。“影子对照”页（只有店主能看）对每笔索赔取处理人员的第一个实质决定（退款、和解、反驳；都没有时取第一条消息），和执行那一刻的判定建议比较，给出一致率、方向相反的笔数（系统建议反驳而人工退款，或反过来）、判定等级 × 人工决定的矩阵和逐笔列表。默认只统计影子模式下的决定，看得到判定时做的决定可以切换进来参考。

## 评估集

开发文档：“评估集……每次修改分析器或权重后重跑，输出各分析器的精确率与召回率，以及真实样本的误判率”。

```bash
npm run eval
```

数据放在临时目录里，跑完删除，不会动 `.data/`。报告写到 `eval-results/<时间>/report.md`，完整数据在同目录的 `results.json`（`eval-results/` 不进 git）。`npm run eval -- --help` 看全部选项。

**标注**按开发文档分四类：合法售后、证据不足、疑似异常、已确认滥用。只有存在可核实的反证（物流、留底、序列号、商家记录）或当事人承认时才标“已确认滥用”；AI 痕迹、检测器概率、画面矛盾只能标“疑似异常”。

**指标：**

| 指标 | 算法 |
|---|---|
| 合法售后被判为中、高风险的比例 | 首要指标。判“证据不足”不算误判 |
| 已确认滥用的精确率、召回率 | 判高风险算预测为滥用 |
| PR-AUC | 按风险分 R 排序的平均精确率。硬规则判的高风险 R 可能低于阈值，报告会列出这些样本 |
| 风险分校准 | R 是信号贡献的加权和，不是概率，按判定阈值分档（< 0、0–1、1–3、≥ 3），看每档的实际滥用比例 |
| 各分析器的精确率、召回率 | 样本级：分析器给出“与索赔矛盾”的信号算标记，疑似异常和已确认滥用算正类 |
| 稳健性 | 同一样本经重新压缩、裁剪、调亮、截图后，判定等级不变的比例，并列出变化的样本和消失的信号 |
| 耗时 | 单个索赔跑完核验管线的中位数、P95、最长 |

**内置样本**是 18 个验收场景（合法售后 7、证据不足 1、疑似异常 7、已确认滥用 3）。它们就是规则和权重设计时对照的场景，属于调参集，指标偏乐观，只能当回归基线。当前结果：

- 合法售后误判 0/7
- 已确认滥用召回率 100%，精确率 60%：“带水印的 AI 编辑”和“证据相互矛盾”被硬规则判为高风险，但按标注规则只算疑似异常
- 四种形式变换的一致率都是 15/16。唯一变化的是“带水印的 AI 编辑”：重新编码会去掉图片里的 C2PA 清单，判定从高风险变成证据不足。C2PA 本来就挡不住重新编码，所以“没有凭证”不能当作真实的证据

内置样本变换时，录制回放按变换后的文件重新登记（假设模型对同样内容给出同样结果），所以一致率反映的是本地分析器和判定规则的稳健性。

**外部样本**用 `--dataset` 指定一个 manifest：

```bash
npm run eval -- --dataset ./my-eval/manifest.json
```

```json
{
  "name": "2026 年 11 月标注",
  "samples": [
    {
      "id": "case-001",
      "label": "legit",
      "split": "test",
      "buyer": "buyer-17",
      "claim": { "type": "damaged", "origin": "portal", "narrative": "杯身有裂纹" },
      "order": {
        "category": "ceramics",
        "amount": 48,
        "currency": "USD",
        "items": [{ "sku": "MUG-01", "title": "青瓷马克杯", "quantity": 1, "weightG": 420 }],
        "shipping": { "weightG": 435 }
      },
      "tracking": { "status": "delivered", "events": [], "deliveredPostalCode": "94107" },
      "evidence": [{ "file": "case-001/overall.jpg", "shot": "overall", "source": "live_capture" }],
      "references": [{ "file": "case-001/ref.jpg", "shot": "overall" }],
      "messages": [{ "sender": "buyer", "text": "杯子有问题" }]
    }
  ]
}
```

- `label`：`legit`、`insufficient`、`suspicious`、`confirmed_abuse`
- `order` 的字段和 `POST /api/orders` 相同，`orderNo` 不填时自动生成
- 文件路径相对 manifest 所在目录，支持 JPEG、PNG、WebP 和视频（视频需要 ffmpeg）
- 样本按 manifest 里的顺序导入同一个库：后面的样本能查到前面样本的图片，跨订单套图检测和真实环境一样生效

**样本隔离：** 同一张图（含重新压缩、裁剪后的近似图，判定标准和 Origin 的复用检测相同）、同一买家、同一 SKU 的样本连成一组，整组只能在一个集合里。手工标了 `split` 却跨集合时，报告标出泄漏，命令以退出码 2 结束；没标的样本按组自动分配（约三成进调参集）。两个集合都有样本时，指标分别统计。

**离线和 `--live`：** 默认离线，不调用 LLM 和检测器，只用录制回放和本地分析器。外部样本没有录制结果，依赖模型的分析器会标为未执行，判定多半是“证据不足”或“核验不完整”。加 `--live` 会读 `.env.local` 里的 LLM 配置并真实调用（产生费用，每种形式变换都会再调用一遍，可以用 `--transforms none` 只跑原样）。

没有覆盖的：二次拍摄、视频转码、文字改写这三种形式变化（需要真实设备或模型），以及“真实退货单但内容不符”这类关联错误。

## 数据最小化

开发文档要求“原始证据文件保留期由商家设置，到期删除；提供按索赔删除全部数据的接口”。

**证据保留期。** 在设置页打开“到期自动删除证据原件”并填天数。
- 只删已结案索赔里买家证据的原件；商家留底照不删。
- 证据记录、SHA-256、感知哈希、信号和判定都保留，所以报告和审计仍然完整，图片复用检测也还能比对。
- 同一个文件还被别的证据引用时（比如复用检测命中的图），文件会留着。
- 保存时立即执行一次，之后服务每小时检查一次。
- 原件删除后，证据位置显示占位图，这笔索赔不能再重新分析：分析器读不到文件，会把原来的信号清掉。

**按索赔删除。** 索赔页底部的“删除这笔索赔的数据”，对应 `DELETE /api/claims/{id}`。
- 会删除买家陈述、证据文件、挑战码、索赔页链接、信号、分析记录、判定、动作记录、时间线，以及这笔争议的 webhook 原文。
- 订单和双方消息属于订单，会保留。
- 只留一条删除记录（索赔编号、争议编号、订单号、时间、操作人），不含买家内容。同步时会跳过已删除的争议，不会把它导回来。
- 以下情况不能删：PayPal 争议还没结案（删了就不能在 Verdict 里回应了）、有结果不明或还在执行的动作、分析还在进行。
- 删除不能撤销，PayPal 上的争议和资金不受影响。

## 商家系统推送订单

开发文档的 `POST /api/orders`，供商家自己的系统推送订单和发货信息。先在 `.env.local` 里设置 `VERDICT_API_KEY`（不设置时接口返回 503，不启用），然后：

```bash
curl -X POST http://127.0.0.1:3000/api/orders \
  -H "Authorization: Bearer $VERDICT_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "orderNo": "SHOP-10001",
    "category": "ceramics",
    "amount": 59,
    "currency": "USD",
    "items": [{ "sku": "MUG-01", "title": "粗陶马克杯", "quantity": 1, "color": "米白", "weightG": 410 }],
    "listingSnapshot": { "title": "粗陶马克杯", "description": "米白色，350ml", "color": "米白" },
    "buyer": { "name": "Jamie", "email": "jamie@example.com" },
    "shipAddress": { "line1": "1 Main St", "city": "Austin", "state": "TX", "postalCode": "73301", "countryCode": "US" },
    "shipping": { "carrier": "UPS", "trackingNumber": "1Z999AA10123456784", "weightG": 455 }
  }'
```

- 新订单返回 201。按 `orderNo` 幂等：同一订单再推只更新 `shipping` 里的物流信息，返回 200 和 `updated` 字段。
- 下单时的商品快照只在第一次保存，之后不会被覆盖（“与描述不符”只和下单时的快照比对）。金额、商品、快照等字段和已存的不同时，会列在 `ignored` 里。
- 物流信息变化时，这笔订单未结案的索赔会重跑 Logistics。
- 买家邮箱只存 SHA-256 哈希。
- 带 `paypal.captureId` 且配好了沙箱时，按沙箱订单处理（争议按捕获 ID 匹配，退款走沙箱）。其他情况走模拟器。
- 还没有接入物流接口，推送的单号没有轨迹，Logistics 会标为未执行。

## 后续争议操作

判定引擎只根据证据给建议，不知道争议走到了哪一步。下面几个操作在 PayPal 给出对应链接时才出现在动作面板里，草稿由 `followUpDraft` 和 `returnOfferDraft`（`src/core/recommend.ts`）生成：

| 操作 | 什么时候出现 | 说明 |
|---|---|---|
| 提出退货退款 `make-offer`（`REFUND_WITH_RETURN`） | PayPal 的和解类型里有 `REFUND_WITH_RETURN`（目前只在“与描述不符”里见到），类目允许退货，买家还没寄回 | 带上商家的退货地址。买家接受后要寄回并填退货单号，之后才出现“确认退货” |
| 向 PayPal 补充说明 `provide-supporting-info` | 争议在 `UNDER_REVIEW` | 追加说明和关键证据图片 |
| 确认退货收货情况 `acknowledge-return-item` | 买家接受退货退款并填了退货单号 | 商家按实际开箱结果选择 `ITEM_RECEIVED`、`EMPTY_PACKAGE_OR_DIFFERENT` 等。默认是“已收到”，系统不会替商家选择负面结果。**选“已收到”后 PayPal 会直接按和解金额退款并结案**，确认框会写明 |
| 申诉 `appeal` | PayPal 判买家胜诉后 | 已结案的索赔只开放这一项；申诉后索赔回到“已执行动作”，PayPal 再次结案时自动关闭 |

模拟器支持补充说明（提交证据后争议进入 `UNDER_REVIEW`，就能看到这一项）和退货退款和解。模拟器没有买家寄回这一步，也没有裁决，所以确认退货和申诉只能在沙箱里试。

## 接 PayPal 沙箱（可选）

只用测试资金，不涉及真实的钱。接口地址写死在 `src/paypal/sandbox.ts` 里，不能通过配置改成正式环境，`PAYPAL_ENV=live` 会被拒绝。

**1. 建沙箱应用**

1. 登录 <https://developer.paypal.com>，在 Sandbox → Accounts 里确认有一个商家（Business）账户和一个个人（Personal）账户。
2. Apps & Credentials → 选 Sandbox → Create App，类型选 Merchant，绑定那个商家账户。
3. 在应用的 Features 里确认 Customer disputes 已启用。

**2. 填配置**

复制 `.env.example` 为 `.env.local`，填入：

```
PAYPAL_ENV=sandbox
PAYPAL_CLIENT_ID=应用的 Client ID
PAYPAL_CLIENT_SECRET=应用的 Secret
```

Secret 只留在 `.env.local` 里，这个文件已被 `.gitignore` 排除。

**3. 检查连接**

打开“设置”页，点“检查连接”。这一步只读，会确认凭据、应用权限和争议接口。

**4. 走一遍流程**

1. 到“订单与留底”，用“沙箱测试下单”下一单，跳到 PayPal 后用个人账户付款。**付款方式要选 Visa。** 默认的银行账户走 eCheck，款项一直待处理、没有卖家保护，部分退款会被拒绝，报告问题时也看不到“没收到货”和“与描述不符”。订单页的“付款状态”会显示这种情况。
2. 用个人账户打开 <https://www.sandbox.paypal.com/disputes/dashboard/>，选这笔交易，点 Report a Problem。选“没收到货”或“与描述不符”，其他类型 Verdict 暂不处理，会在设置页列为已跳过。
3. 等大约 3 分钟。Verdict 每分钟同步一次，也可以在索赔页点“同步 PayPal 沙箱”。
4. 打开带“沙箱”标记的索赔，查看判定，确认后执行动作。

实际联调时量到的时间（2026-11-05，样本只有几笔）：

- 新争议先是 `OPEN`、`UNDER_REVIEW`，只有 `self` 链接，大约 3 分钟后才变成 `WAITING_FOR_SELLER_RESPONSE`，这时才能回应。
- 列表接口比详情接口慢，第一笔争议过了约 165 秒才出现在列表里。结案也一样，所以结案可能要多等一轮同步。
- 每次写操作后，争议会有 10 到 40 秒的 `UNDER_REVIEW`，这段时间不能操作。界面会提示稍后刷新。
- 买家接受和解后，约 2 分钟才变成 `RESOLVED`。中间约 10 秒里 `accept_claim` 链接会短暂出现，这时点接受索赔的结果没有测过。
- 要测退货流程：开“与描述不符”争议时，“是否愿意退回商品”选 Yes，PayPal 就给出了 `REFUND_WITH_RETURN`（选 No 时还会不会给没有测过）。商家提出退货退款、买家接受后，买家要在案件页点 Add Tracking Info 填退货单号和一句留言，之后商家才能确认退货。

索赔页的“沙箱测试工具”只在 PayPal 给出 `require-evidence` 或 `adjudicate` 链接时才有按钮。这两个链接出现得很晚：拒付阶段的争议提交证据后 5 分钟还没有，十几个小时后再看才出现，所以不能指望用它快速推进状态。

同一个沙箱买家反复开争议时，Behavior 分析器会累积“索赔频率偏高”的信号（买家风险上升），这是正确的行为，但看判定时要知道它受测试次数影响。

同一笔交易只能开一次争议，关闭后也不能再开，每测一个场景都要重新下单。没有从 Verdict 下单的交易（比如手工转账）也能同步，系统会自动导入一笔最小订单。

**Webhook（可选）**

本地开发不需要。Verdict 靠定时同步拉取争议，不用配隧道。要测 webhook 时：

1. 用隧道把本地端口暴露成 HTTPS 地址（PayPal 不能回调 localhost）。
2. 在应用的 Sandbox Webhooks 里添加 `https://你的地址/webhooks/paypal`，订阅 `CUSTOMER.DISPUTE.CREATED`、`UPDATED`、`RESOLVED`。
3. 把 Webhook ID 填到 `PAYPAL_WEBHOOK_ID`。

有社区反馈沙箱的争议 webhook 不一定会触发，所以不要依赖它。

**结果不明的动作**

PayPal 的争议接口不支持 `PayPal-Request-Id`，所以遇到超时、断连或 5xx 时，请求可能已经生效。这种动作会标记为“结果不明”，这笔索赔随后不能再执行任何动作，直到你对照 PayPal 后台标记“已生效”或“没有生效”。系统不会自动重试，以免重复退款。

**用真实沙箱验证过的地方（2026-11-05）**

| 地方 | 结果 |
|---|---|
| 连接检查、下单跳转、`localhost` 回跳、捕获响应 | 通过 |
| 争议同步、按 `custom` 匹配本地订单、状态变化写入时间线 | 通过 |
| 争议链接的 `rel` | 实际用下划线（`make_offer`、`provide_evidence`），代码两种写法都认 |
| 发送消息（中文） | 通过。发送后 `make_offer` 链接会消失 |
| 提交证据 | multipart 的 `input` 和 `file1` 通过。PayPal 收下了图片、物流单号和中文说明。在 `WAITING_FOR_BUYER_RESPONSE` 和拒付阶段也能提交，和文档只允许 `WAITING_FOR_SELLER_RESPONSE` 的说法不同，所以 Verdict 按链接判断 |
| 升级争议 | 通过，升级后进入 `CHARGEBACK` |
| 提出和解 | 通过，`seller_offered_amount` 记录正确，买家端能看到中文说明 |
| 买家接受和解后同步 | 通过，本地索赔自动结案，结果为 `RESOLVED_BUYER_FAVOUR` |
| 部分退款、退完余额 | 通过，捕获依次变成 `PARTIALLY_REFUNDED`、`REFUNDED` |
| 被拒绝的退款（超额、eCheck 付款的部分退款） | PayPal 返回 4xx，Verdict 记为“失败”，不是“结果不明”，错误信息带 issue 和 debug_id |
| 补充说明（`provide-supporting-info`） | multipart 的 `input` 为 `{"notes": ...}`、文件 `file1` 通过。PayPal 记在 `supporting_info` 里，中文说明和图片都在 |
| 附核验报告 PDF | 通过。`verdict-report.pdf` 排在第一个，PayPal 存下的文件下载回来完整，中文和标点正常 |
| 沙箱测试工具“要求商家举证” | 通过，约 25 秒后回到 `WAITING_FOR_SELLER_RESPONSE`，重新出现 `provide_evidence` |
| 接受索赔 | JSON `{"note": ...}` 通过（接口参考只列了 multipart，指南的 JSON 写法是对的）。约 2 分钟后 `RESOLVED`，全额退款，结果为 `SELLER_ISSUED_REFUND` |
| 沙箱测试工具“裁决” | `BUYER_FAVOR` 通过，约 160 秒后 `RESOLVED`，结果 `RESOLVED_BUYER_FAVOUR`，Verdict 同步后自动结案。链接要等十几个小时才出现 |
| 拒付阶段提交 `PROOF_OF_FULFILLMENT` | 询问阶段没交过物流证据的争议，升级后带物流单号、报告 PDF 提交通过 |
| 退货退款和解（`REFUND_WITH_RETURN`） | `return_shipping_address` 通过，买家端能看到退货地址和中文说明，接受后要求买家寄回并填写退货单号 |
| 确认退货（`acknowledge-return-item`） | 买家填完退货单号约 40 秒后出现链接。JSON `{"note", "acknowledgement_type": "ITEM_RECEIVED"}` 通过，约 2 分钟后 `RESOLVED`，PayPal 自动退款，结果 `RESOLVED_BUYER_FAVOUR`、原因 `INQUIRY_OFFER_REFUND_WITH_ITEM_RETURN` |

**还没有用真实沙箱验证的地方**

| 地方 | 说明 |
|---|---|
| Webhook 验签和回调 | 没有配置 `PAYPAL_WEBHOOK_ID`，本地也收不到回调。只用模拟响应测过 |
| 重复提交同类证据 | 询问阶段交过 `PROOF_OF_FULFILLMENT` 的争议，拒付阶段再交同一类型返回 `EVIDENCE_TYPE_IS_NOT_ALLOWED`，一分钟后用同样的附件改交 `OTHER` 通过；没交过的争议则能交。所以判断是同类型不能重复提交，但只各有一个样本。动作面板现在会自动改用 `OTHER`、把物流单号写进说明，PayPal 仍然拒绝时错误信息会说明原因 |
| “结果不明”的处理 | 没有遇到真实的超时或 5xx，只用模拟响应测过 |
| 确认退货的负面结果 | 只试了 `ITEM_RECEIVED`。选损坏、空包裹、少件、没收到时 PayPal 怎么处理（是否转人工审核）没有测过；这些选项也不附验收照片 |
| 申诉（`appeal`） | 按提交证据的 `evidences` 结构实现。裁决买家胜诉后没有出现 `appeal` 链接：PayPal 文档说沙箱里只有买家邮箱含 `allowappeal` 的争议才能申诉，现在的测试买家邮箱不含这个词。要测的话，在 developer.paypal.com 的 Sandbox → Accounts 里把个人账户邮箱改成含 `allowappeal` 的地址（或新建一个），用它付款开争议 |

**和开发文档的差异**

- 文档假设 `PayPal-Request-Id` 能保证所有写操作幂等，实际只有退款和下单支持，所以加了“结果不明”处理。
- 文档的报告导出选型是 `@react-pdf/renderer`，这里用的是 `pdfkit`：不依赖 React 渲染器，便于在动作执行器里直接生成。
- 文档的 `demo-shop` 做成了订单页上的“沙箱测试下单”。
- 确认退货目前不附验收照片；申诉和补充说明可以附报告和证据图片。
- 退货退款和解的退货地址在设置页填写，没有填写时用演示仓库地址（虚构）。
- “接受索赔”只发全额 `REFUND`，没有用 PayPal 提供的 `REFUND_WITH_RETURN` 和 `PARTIAL_REFUND` 类型，要退货时用“提出退货退款”。

## 用手机测试摄像头

浏览器只在 HTTPS 下开放摄像头，所以要用：

```bash
npm run dev:phone
```

然后：

1. 手机和电脑连同一个 Wi-Fi。
2. 在电脑上用**局域网 IP** 打开控制台（如 `https://192.168.1.5:3000`），不要用 localhost，否则生成的链接手机打不开。
3. 生成索赔链接，发到手机上打开。

注意：

- 这个模式会把控制台暴露给同一网络里的所有设备。控制台有登录保护，但开发服务器不适合长时间对外，用完请关掉。
- `--experimental-https` 第一次运行时会用 mkcert 生成证书，可能要求你输入系统密码来信任本地证书。
- 手机上会看到证书警告。iOS Safari 对这种证书的摄像头支持可能不稳定，打不开时可以用相册上传。
- 这条路径没有在真机上验证过，我只用画布模拟的视频流测过拍摄和录视频流程。手机浏览器的 MediaRecorder 输出格式各不相同（iOS Safari 是 MP4，Android Chrome 多为 WebM），服务端两种都收。

## 没有做的

- PayPal 正式环境：只支持沙箱
- 多商家：账号属于一个商家，没有平台级的多商家隔离
- 登录方式只有邮箱和密码，没有两步验证、单点登录，也不会发邮件（邀请和重置链接由店主自己转发）
- 限流计数和会话校验都在单个进程里，多实例部署要换成 Redis 之类的共享存储
- `APP_ENCRYPTION_KEY` 不支持轮换：换密钥后，设置页保存的凭证要重新填
- 由 LLM 撰写的报告和草稿：目前是确定性模板
- Postgres、BullMQ、S3：MVP 用 SQLite、进程内任务和本地磁盘代替，模块边界按原方案划分，之后可以替换

## 上线前必须重新校准

**图片复用阈值（`REUSE_DISTANCE`）。** 命中后是硬规则，会直接判高风险。目前的 40 只在程序生成的图上校准过：同图经压缩、裁剪、调亮后距离 35 到 45，同模板的不同面单最小 55。真实照片（尤其同店铺、同背景的商品图）的分布可能不同。我选了偏严的一侧，代价是重度编辑过的复用图可能漏检。

**判定阈值。** 下面“开发文档的缺口”里列出的数值都是暂定的，没有真实数据支撑。改动阈值和权重前后各跑一次 `npm run eval -- --dataset 你的测试集`，对比首要指标（合法售后的误判率）和已确认滥用的召回率。

## 开发文档的缺口

实现时遇到这些问题，需要产品确认：

**文档内部冲突**

1. 文档的默认权重下，相册上传的中等强度信号最高只有 0.9，到不了中风险阈值 1，但验收表要求这类场景判中风险。我加了“中风险下限”规则（`MEDIUM_FLOOR_CODES`）。
2. 文档写的判定顺序把充分性检查放在打分之前，这样“R 高但 Q 低”的分支永远走不到。我调整为有风险证据时先看风险。
3. 验收表的“检测服务不可用”场景只去掉了检测器，而文档另一处的降级规则写的是 Provenance 和 Synthetic 都不可用，两种说法不一致。现在的做法：任一适用分析器没跑就标“核验不完整”；只有关键分析器组全部不可用时才阻止判低风险。
4. 扩展部分说卖家伪造单号是“第六类”威胁，但它在表里是第 8 行。

**文档没有给数值，我暂定的**

- Q 充足的阈值 0.5，M 高的阈值 0.5
- M 的权重：SKU 偏差 0.35、批次 0.3、详情页改动 0.2、缺留底 0.15
- 哪些命题算“关键”（见 `src/core/catalog.ts`）

**和当前 Claude API 不符**

- 文档要求 `temperature` 取 0，但当前模型会拒绝这个参数并返回 400，所以我去掉了。需要稳定输出的部分靠确定性规则和结构化输出保证。

**数据模型补充**

- 文档的数据模型没有消息、时间线、感知哈希和用量记录，我加了对应的表和字段。

**建议再看一眼的规则**

- `IDENTITY_MISMATCH` 是硬规则，但仓库错发也会触发。目前只靠报告里的“需排除的正常解释”提醒商家。如果错发在你们的场景里常见，建议改成不直接判高风险。
