# Verdict MVP

Verdict 帮 PayPal 商家处理争议和退款：收集买家证据，判断真实性和充分性，给出带理由的报告。资金动作必须由商家确认后才执行。

这是可以直接试用的最小版本，不需要任何账号、密钥或外部服务。默认情况下 PayPal 和物流都由内置模拟器代替，**不产生真实资金流动**。也可以[接 PayPal 沙箱](#接-paypal-沙箱可选)，用测试资金走真实接口。

## 运行

需要 Node.js 22.13 或更高版本。

```bash
npm install
```

```bash
npm run dev
```

打开 <http://127.0.0.1:3000>。首次访问会自动生成演示数据，存放在 `.data/`。

其他命令：

| 命令 | 作用 |
|---|---|
| `npm test` | 运行判定引擎、18 个验收场景、服务端和 PayPal 沙箱客户端的测试（沙箱测试用模拟响应，不访问网络） |
| `npm run typecheck` | 类型检查 |
| `npm run reset` | 删除 `.data/`，下次启动时重新生成（需先停止服务）。也可以在“设置”页重置 |
| `npm run dev:phone` | 用手机测试摄像头，见下文 |

## 三种试法

**1. 看验收场景。** 索赔列表里的 18 笔对应开发文档的验收表。每笔都标了场景和文档期望，可以和实际判定对照。

**2. 走一遍买家流程。** 进入“订单与留底”，打开一笔订单，点“生成索赔链接”，再打开买家页面：确认订单、选问题类型、逐镜头拍摄（每个镜头有随机挑战码）、提交。回到商家端可以看到分析器逐项完成、判定随之更新。电脑没有摄像头时，可以从相册选择，这类证据按 C 层降权。

**3. 试你自己的图片。** 点“手动导入”，上传一张 ChatGPT 生成的图或任意照片。没有配置 LLM 时，只有本地分析器会运行，判定会标“核验不完整”并列出没跑的检查。

在订单页点“模拟 PayPal 争议”，可以走完 webhook 验签、去重、拉取详情、建索赔的流程。

## 哪些是真的，哪些是模拟的

| 部分 | 状态 | 说明 |
|---|---|---|
| 判定引擎、硬规则、R/Q/M 计算 | 真实运行 | 确定性规则，同样的输入得到同样的结果 |
| Provenance | 真实运行 | 按字节扫描 C2PA 和 AIGC 隐式标识。只判断是否存在，**不校验签名** |
| Origin | 真实运行 | 256 位感知哈希，比对本商家历史证据。反向搜图未接入 |
| Logistics、Behavior | 真实运行 | 逻辑是真的，物流数据来自模拟器（沙箱订单也一样） |
| 动作执行、幂等、确认校验、token | 真实运行 | 只有 `src/server/actions.ts` 能调用 PayPal 写接口，由测试保证 |
| PayPal | **模拟**，可接沙箱 | 18 个演示场景始终走模拟器。配置沙箱后，沙箱订单调用真实的 PayPal 沙箱接口。不支持正式环境 |
| 演示场景的视觉分析和检测器结果 | **录制回放** | 18 个场景的结果预先写入缓存，走和真实调用相同的代码路径，界面标“录制回放” |
| 你上传的真实图片的视觉分析 | 默认不运行 | 需要配置 LLM，见下文 |
| AI 生成检测器、SynthID | 未接入 | 真实图片的 Synthetic 显示“未执行” |

演示图片都是程序画的占位图，右下角标有“演示占位图”。

## 接入 Claude（可选）

复制 `.env.example` 为 `.env.local`，填入：

```
LLM_PROVIDER=anthropic
LLM_API_KEY=你的密钥
```

配置后，真实照片会经过 Consistency、Plausibility、Reference、Records。**图片会发送给 Anthropic 处理**，索赔页会在提交前告诉买家。这条路径默认使用 `claude-opus-5-5`，并开启了服务端模型回退：主模型不可用时，请求可能由其他模型处理。这段适配器还没有用真实 API 验证过。

## 接 PayPal 沙箱（可选）

只用测试资金，不涉及真实的钱。接口地址写死在 `src/paypal/sandbox.ts` 里，不能通过配置改成正式环境，`PAYPAL_ENV=live` 会被拒绝。

**1. 建沙箱应用**

1. 登录 <https://developer.paypal.com>，在 Sandbox → Accounts 里确认有一个商家（Business）账户和一个个人（Personal）账户。
2. Apps & Credentials → 选 Sandbox → Create App，类型选 Merchant，绑定那个商家账户。
3. 在应用的 Features 里确认 Customer disputes 已启用。

**2. 填配置**

复制 `.env.example` 为 `.env.local`，填入：

```
PAYPAL_ENV=sandbox
PAYPAL_CLIENT_ID=应用的 Client ID
PAYPAL_CLIENT_SECRET=应用的 Secret
```

Secret 只留在 `.env.local` 里，这个文件已被 `.gitignore` 排除。

**3. 检查连接**

打开“设置”页，点“检查连接”。这一步只读，会确认凭据、应用权限和争议接口。

**4. 走一遍流程**

1. 到“订单与留底”，用“沙箱测试下单”下一单，跳到 PayPal 后用个人账户付款。
2. 用个人账户登录 <https://www.sandbox.paypal.com>，找到这笔交易并报告问题。选“没收到货”或“与描述不符”，其他类型 Verdict 暂不处理，会在设置页列为已跳过。
3. 等几分钟。Verdict 每分钟同步一次，也可以在索赔页点“同步 PayPal 沙箱”。
4. 打开带“沙箱”标记的索赔，查看判定，确认后执行动作。
5. 新争议一开始可能是 `UNDER_REVIEW`，不能回应。这时用索赔页上的“沙箱测试工具”推进状态：“要求商家举证”后就能提交证据，“裁决”可以直接结案。

同一笔交易只能开一次争议，关闭后也不能再开，每测一个场景都要重新下单。没有从 Verdict 下单的交易（比如手工转账）也能同步，系统会自动导入一笔最小订单。

**Webhook（可选）**

本地开发不需要。Verdict 靠定时同步拉取争议，不用配隧道。要测 webhook 时：

1. 用隧道把本地端口暴露成 HTTPS 地址（PayPal 不能回调 localhost）。
2. 在应用的 Sandbox Webhooks 里添加 `https://你的地址/webhooks/paypal`，订阅 `CUSTOMER.DISPUTE.CREATED`、`UPDATED`、`RESOLVED`。
3. 把 Webhook ID 填到 `PAYPAL_WEBHOOK_ID`。

有社区反馈沙箱的争议 webhook 不一定会触发，所以不要依赖它。

**结果不明的动作**

PayPal 的争议接口不支持 `PayPal-Request-Id`，所以遇到超时、断连或 5xx 时，请求可能已经生效。这种动作会标记为“结果不明”，这笔索赔随后不能再执行任何动作，直到你对照 PayPal 后台标记“已生效”或“没有生效”。系统不会自动重试，以免重复退款。

**还没有用真实沙箱验证的地方**

下面这些都只用模拟的 PayPal 响应测过。官方文档有矛盾或没写清楚的地方，我按最可能的写法实现，第一次联调时要重点看：

| 地方 | 现在的写法 | 不确定的原因 |
|---|---|---|
| 提交证据的文件字段名 | `file1`、`file2` | 指南的 curl 用 `file1`，接口参考写的是 `evidence-file` |
| 接受索赔的请求格式 | JSON `{"note": ...}` | 指南是 JSON，接口参考只列了 multipart |
| 下单跳转 | `payment_source.paypal.experience_context`，取 `payer-action` 或 `approve` 链接 | 我查到的文档片段没有确认这些字段 |
| 捕获响应 | `purchase_units[0].payments.captures[0]`、`payer`、`shipping` | 同上 |
| 回跳地址 | `http://localhost:3000/api/paypal/return` | 不确定 PayPal 是否接受 localhost。不行时配置 `PUBLIC_URL` 用隧道地址 |
| 争议链接的 `rel` 名称 | 同时按 href 结尾和 rel 匹配 | 文档里只有占位示例 |
| 非英文的说明文字 | 中文直接发送 | 文档没有说明字段是否限制字符集 |

**和开发文档的差异**

- 文档假设 `PayPal-Request-Id` 能保证所有写操作幂等，实际只有退款和下单支持，所以加了“结果不明”处理。
- 文档要求附核验报告 PDF，目前没有 PDF 生成，改为附反驳信号引用的证据图片。
- 文档的 `demo-shop` 做成了订单页上的“沙箱测试下单”。
- 没有实现 `provide-supporting-info`、`appeal`、`acknowledge-return-item`。遇到这些状态请到 PayPal 后台处理。

## 用手机测试摄像头

浏览器只在 HTTPS 下开放摄像头，所以要用：

```bash
npm run dev:phone
```

然后：

1. 手机和电脑连同一个 Wi-Fi。
2. 在电脑上用**局域网 IP** 打开控制台（如 `https://192.168.1.5:3000`），不要用 localhost，否则生成的链接手机打不开。
3. 生成索赔链接，发到手机上打开。

注意：

- 这个模式会把没有登录保护的控制台暴露给同一网络里的所有设备，用完请关掉。配置了 PayPal 沙箱时，他们还能操作你的沙箱账户。
- `--experimental-https` 第一次运行时会用 mkcert 生成证书，可能要求你输入系统密码来信任本地证书。
- 手机上会看到证书警告。iOS Safari 对这种证书的摄像头支持可能不稳定，打不开时可以用相册上传。
- 这条路径没有在真机上验证过，我只用画布模拟的视频流测过拍摄流程。

## 没有做的

- PayPal 正式环境：只支持沙箱
- 登录和多商家权限：控制台没有登录，默认只监听 127.0.0.1
- 视频证据：只支持照片
- PDF 报告：报告是可打印的网页，用浏览器“存为 PDF”
- 由 LLM 撰写的报告和草稿：目前是确定性模板
- Postgres、BullMQ、S3：MVP 用 SQLite、进程内任务和本地磁盘代替，模块边界按原方案划分，之后可以替换

## 上线前必须重新校准

**图片复用阈值（`REUSE_DISTANCE`）。** 命中后是硬规则，会直接判高风险。目前的 40 只在程序生成的图上校准过：同图经压缩、裁剪、调亮后距离 35 到 45，同模板的不同面单最小 55。真实照片（尤其同店铺、同背景的商品图）的分布可能不同。我选了偏严的一侧，代价是重度编辑过的复用图可能漏检。

**判定阈值。** 下面“开发文档的缺口”里列出的数值都是暂定的，没有真实数据支撑。

## 开发文档的缺口

实现时遇到这些问题，需要产品确认：

**文档内部冲突**

1. 文档的默认权重下，相册上传的中等强度信号最高只有 0.9，到不了中风险阈值 1，但验收表要求这类场景判中风险。我加了“中风险下限”规则（`MEDIUM_FLOOR_CODES`）。
2. 文档写的判定顺序把充分性检查放在打分之前，这样“R 高但 Q 低”的分支永远走不到。我调整为有风险证据时先看风险。
3. 验收表的“检测服务不可用”场景只去掉了检测器，而文档另一处的降级规则写的是 Provenance 和 Synthetic 都不可用，两种说法不一致。现在的做法：任一适用分析器没跑就标“核验不完整”；只有关键分析器组全部不可用时才阻止判低风险。
4. 扩展部分说卖家伪造单号是“第六类”威胁，但它在表里是第 8 行。

**文档没有给数值，我暂定的**

- Q 充足的阈值 0.5，M 高的阈值 0.5
- M 的权重：SKU 偏差 0.35、批次 0.3、详情页改动 0.2、缺留底 0.15
- 哪些命题算“关键”（见 `src/core/catalog.ts`）

**和当前 Claude API 不符**

- 文档要求 `temperature` 取 0，但当前模型会拒绝这个参数并返回 400，所以我去掉了。需要稳定输出的部分靠确定性规则和结构化输出保证。

**数据模型补充**

- 文档的数据模型没有消息、时间线、感知哈希和用量记录，我加了对应的表和字段。

**建议再看一眼的规则**

- `IDENTITY_MISMATCH` 是硬规则，但仓库错发也会触发。目前只靠报告里的“需排除的正常解释”提醒商家。如果错发在你们的场景里常见，建议改成不直接判高风险。

## 目录结构

```
src/core/        判定引擎、规则目录、建议动作（纯函数，无外部依赖）
src/analyzers/   九个分析器
src/providers/   LLM、检测器、物流的适配层
src/paypal/      PayPalClient 接口、模拟器和沙箱客户端
src/server/      数据库、存储、token、分析流水线、动作执行器、webhook、沙箱同步
src/demo/        演示图片和 18 个场景
src/components/  界面组件
src/app/         页面和 API 路由
tests/           测试
```
